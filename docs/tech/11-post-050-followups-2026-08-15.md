## Task 1 — `standing` must not be writable by the model

**This is a defect, not a preference.** It is an effects channel that contradicts the spec's own stated reason for a decision it already took.

### The evidence

`GroupHolder.standing` (`src/domain/holder.ts:19`) is a number seeded at `0.5` by bootstrap (`src/atomic/bootstrap.ts:49`). It does two effectful things:

- gates carriage delivery — `src/core/derive-beliefs.ts:121`, `if (c.minStanding !== undefined && standing < c.minStanding) continue`
- feeds the `socialPosition` salience factor — `src/core/derive-beliefs.ts:157`

The model can set it. `sneq__commit_narrative.holders[]` accepts `standing: z.number()` on the GROUP branch (`src/tools/schemas.ts:142`); `decideCommitNarrative` passes the array straight through (`src/core/commit-narrative.ts:296`, `holders: bundle.holders ?? []`); the executor upserts it (`src/atomic/commit-narrative.ts:99`).

So a model can raise a holder's standing and thereby hand that holder news the `minStanding` gate was withholding. That is the model writing an effect.

### Why it is a contradiction and not just a gap

§5.3 of the spec adjudicated `upsert-holder` as a **CLI special case rather than an eleventh tool**, and the stated reason was:

> holder authoring is a host/setup concern, not a narration-loop concern, and the §11 pipeline puts holder creation in `commit_narrative`'s `holders[]` for in-play creation anyway.

Both halves are in the code, and together they undo the first. Holder authoring was declared host-only, and then the narration loop was given a writer for the one field that carries an effect.

### The fix

Split along the line §5.3 already drew. The bundle's `holders[]` may **create** a holder; it may not change the `standing` of one that already exists. The host path (`campaign.upsertHolder`, `src/campaign.ts:377`, reached by the CLI at `src/cli/run.ts:157`) keeps full authority.

Decide and write down which of these the create path does, because they are not the same:

- reject a bundle that sets `standing` on an existing holder (loud, matches the invention-token guard's posture), **or**
- accept the holder and ignore the `standing` field, keeping the stored value (silent, non-breaking).

Recommendation: **reject**, with a `SneqValidationError` naming `upsert-holder` as the corrective call. A silent ignore is the failure mode this whole release exists to remove. Note the invention guard is fail-closed and atomic, so this would be consistent.

Watch the lazy auto-`PARTICIPANT` path (`src/campaign.ts:569`) — it materializes an `IndividualHolder`, which carries `standingOverride`, not `standing`. Decide whether `standingOverride` deserves the same treatment. It is the same class of field on the individual branch (`src/tools/schemas.ts:150`).

**Gate:** a test that a bundle raising an existing group's `standing` is refused, and one that the CLI `upsert-holder` path still sets it.

## Task 2 — count `gravity`, do not police it

**Not a violation. An unaudited channel.**

`sneq__commit_narrative.event.gravity` is `0|1|2|3` from the model (`src/tools/schemas.ts:69`). It is 40% of salience (`src/core/salience.ts:11,23`) and gates all auto-dispatch (`src/core/commit-narrative.ts:171`).

### Why this is not the violation the issue first called it

The consuming design's own doctrine ([experimentation-1#8](https://github.com/JeanDes-Code/experimentation-1/issues/8)) splits three ways: the GM **writes prose**, **answers closed questions**, and **never writes state**. A 0–3 band is a closed question — it is precisely the shape that doctrine licenses. The original filing also objected that four bands is one more than that design settled on, and the author has since withdrawn that as a constraint of the consuming design which has no business becoming an engine constraint for everyone else.

Nothing in the ledger can derive gravity. No event says how much a thing mattered; that is a narrative judgement, and the model is the right source for it. So do not try to derive it, and do not try to constrain it.

### What is actually missing

There is no audit. A model that always answers `3` floods dispatch; one that always answers `0` makes the world silently deaf, because dispatch only fires above `0` (`commit-narrative.ts:171`). `doctor` counts uncovered and unroutable routes but never looks at the distribution that produces them.

Apply the move already made for `OUT_OF_BAND` (#22) and for the `public` tag: **do not lock it, count it.**

### The fix

A `gravity-distribution` check in `src/core/doctor.ts` — the file has 23 checks and an established shape: pure function, `DoctorInput` gathers, `runDoctor` judges, every FAIL names the corrective call. `INFO` exists for lines that report without judging, and is excluded from the roll-up.

Report the histogram over the campaign's events, and flag the two degenerate shapes:

- everything at `0` — the world cannot talk, and no other counter shows it
- everything at the top band — every event dispatches, and the fan-out cap is doing the thinking

`DoctorInput.events` is already passed in, so this needs no new gathering in `campaign.doctor()` (`src/campaign.ts`).

**Gate:** three tests — a healthy spread passes, all-zero flags, all-max flags.

## Refused, with reasons — do not re-open without new evidence

### `standing` derived rather than stored

[experimentation-1#6](https://github.com/JeanDes-Code/experimentation-1/issues/6) requires standing be derived and cached, never stored, on the grounds that *a score cannot be argued with and the design requires that it can*. Good property, wrong layer.

Derived **from what?** There is no ledger signal for social position — no event records that the miller gained standing, and inventing one would mean the engine deciding what raises a person in the world's eyes, which is exactly the fiction semantics SNEQ owns none of. The arguing happens in the consumer's fiction; it can derive standing there and pass the number in. Keep it stored.

### `sharedWith` on `HolderContext`

The ask: for each belief handed to a holder, a boolean for *does anyone else at this holder's `placeId` hold it?* Motivated by real transcript evidence — the two best lines in a 25-transcript sample were true statements of reach.

Refused in that shape, for two reasons, one of which the ask does not name.

**It is a leak by construction.** The boolean reports another holder's knowledge state, which is the exact class of thing the seam exists to withhold. The author's own honest limit — that the no-leak argument comes from one fixture where every holder's town is common ground to them — is the whole problem, not a footnote. It fails for a holder ignorant of their own community's strata, and nothing in the type system says a campaign will not have one.

**And it is expensive on the hot path.** `deriveBeliefs` is a pure derivation over the whole ledger, run on every read, with no cache (`doctor` says so out loud). Computing this per belief means O(holders at place × ledger) on every `getHolderContext`.

If it is wanted later, it should be an explicit separate call the host opts into — `sharedAtPlace(holderId, subject)` — so both the cost and the disclosure are visible at the call site instead of riding every read. **Build the second fixture first**: a campaign with a holder ignorant of their own community's strata, and see whether the boolean still leaks nothing.
